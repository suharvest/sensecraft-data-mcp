# Industrial HTTP API contract

All endpoints return JSON. Successful responses use `{ "ok": true, "data": ... }`; failures use `{ "ok": false, "error": { "code": string, "message": string, "details"?: unknown } }`.

`GET /api/industrial/config` returns the persisted configuration. MQTT passwords are returned as `"********"` plus `passwordConfigured`; MCP endpoint tokens are masked in the same way and include `endpointConfigured`. An empty password or endpoint in `PUT` explicitly clears it; masked placeholders preserve the stored secret.

`PUT /api/industrial/config` accepts the full config (or a partial object), validates it, atomically persists it, resets device runtimes, and reconnects MQTT. Its response is `{ "ok": true, "data": { "config": <masked config>, "validation": { "valid": true } } }`. MQTT/MCP objects are merged; supplied devices replace the device array. The default persisted file is `industrial-config.json` in the process working directory, overridden by `INDUSTRIAL_CONFIG_PATH`. It may contain credentials and must not be committed.

`GET /api/industrial/status` returns `{ broker, devices }`. Devices contain `id`, `name`, `state: "unknown"|"online"|"offline"`, optional `lastMessageAt`, `lastGoodAt`, `ageSeconds`, `retained`, plus `values`, `fieldStatus`, `partial`, `alarms`. Each field's `fresh`/`stale` is recomputed as time expires; retained last accepted values can be historical. `partial` means some fields are fresh and others stale. `lastMessageAt` exposes the latest matching message time; `ageSeconds` measures the last non-retained message.

`notification` is optional global configuration: `{ enabled, deviceType: "watcher"|"d1001", baseUrl, token, mode: "context"|"speak", context, timeoutMs }`. `context` is limited to 25 UTF-8 bytes and rendered `speak` text to 512 UTF-8 bytes. Tokens are masked as `"********"` and are never returned in delivery records or errors. Rules may provide `messageTemplate` using only `{device}`, `{field}`, `{value}`, `{unit}`, `{rule}` substitutions. Alarm activation sends one idempotent `POST <baseUrl>/api/wake` with `{ request_id, mode, text, ttl_ms: 15000 }`; only HTTP 202 is accepted, while 200 is recorded as an unexpected status. Recovery permits a later activation. `context` sends only the short cue, while `speak` sends the rendered message and requires a compatible self-hosted TTS server. `GET` or `POST /api/industrial/notification/test` only probes `GET /api/wake/status`; it never wakes the device. Its normalized result is `{ reachable, available, enabled, authenticated?, state?, reason?, maxContextBytes, maxSpeakBytes, modeSupported, status, auth: "valid"|"unknown"|"invalid", capabilities: { context, speak, speak_backend?, max_context_bytes?, max_speak_bytes? }, deviceType }`; `available` is false when local config, firmware enabled state, or selected mode capability is unavailable. A 200 status without `authenticated:true` does not prove the token is valid. Explicit `POST /api/industrial/notification/send-test` accepts `{ notification?: <notification>, text }`, where `notification` is an unsaved draft merged with the current configuration, and returns `202` when accepted, `409` when the device is busy, or `502` on device/network rejection. Structured error codes include `notification_disabled`, `mode_unsupported`, `auth_failed`, `busy`, `text_too_long`, and `unexpected_status`; HTTP 501 maps to `mode_unsupported`, while HTTP 404 maps to `notification_disabled` only when the response explicitly reports a disabled device state. Unclassified failures use `notification_failed`. Status includes at most 100 recent delivery records with `accepted`/`failed` state.

`onlinePolicy: "message"` measures non-retained message-link activity: bad-quality traffic can keep a device online while fields are stale. `valid_data` (also the default when omitted) requires at least one fresh accepted field. Bad quality cannot establish field freshness; another fresh field may still keep a multi-field device online. A configured broker must also be connected. Retained messages do not refresh live-message time or field validity. Values with bad quality, stale/invalid source timestamps, duplicate/out-of-order source time, or invalid types do not replace accepted values and cancel affected pending duration checks.

`GET /api/industrial/messages` returns `{ items: [{ topic, payload, receivedAt, retained, simulated }], limit }`, newest first.

`POST /api/industrial/preview` accepts `{ topic, payload, retained? }`, selects the first matching device and returns `{ deviceId?, matched, values, validity?, alarms, ignoredFields }`. `validity` predicts per-field acceptance. Alarm candidates carry `durationSeconds` and `pending: true` for positive durations: these predict thresholds, not elapsed-duration or recorded alarms. Retained previews produce no alarm candidates. Preview never changes device state, live message cache or alarm history.

`POST /api/industrial/demo` accepts the same message shape and explicitly marks the message as `simulated: true`; it evaluates the message in an isolated simulation result and never updates the live message cache, device state, alarms, or MQTT broker.

Devices may define `qualityPath`, `goodQualityValues`, `timestampPath`, and `onlinePolicy` (`message` or `valid_data`). Fields may override topic, identity, quality and timestamp mappings. A required source timestamp must be within the device timeout, no more than five seconds ahead, and newer than the prior accepted source time.

The three read-only MCP tools enforce `queryable`. `list_industrial_devices` exposes status and queryable field labels without values. `get_industrial_reading` rejects non-queryable/ambiguous fields, returns candidates for ambiguous devices, and includes accepted `receivedAt`/`sourceTimestamp`, latest message time/quality, `source: "mqtt"`, and current `fresh`/`stale`. `list_industrial_alarms` filters alarms to queryable fields and provides `dataFresh`; stale input does not mean an active alarm recovered.

Device values, pending checks and alarm history reset on configuration changes and restart. Alarm storage retains active alarms plus up to 200 recovered entries when a new activation is recorded; it is not a durable audit log. Messages are memory-only: default cache 200, configurable by `INDUSTRIAL_MESSAGE_CACHE_SIZE` (1–1000); list limit is 1–500. Message cache resets on restart but is not cleared by configuration changes. Preview/demo results never enter either history.
